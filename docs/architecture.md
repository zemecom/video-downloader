# Архитектура YTD PHP: Подробное руководство

Проект представляет собой консольную обертку над `yt-dlp` и `ffmpeg` с продвинутой маршрутизацией прокси и поддержкой браузерного расширения через Native Messaging. Архитектура построена на четком разделении обязанностей, что контролируется статическим анализатором слоев **Deptrac**.

Ниже приведено детальное описание каждого логического модуля в директории `src/`.

---

## 1. Точка входа и Runtime (Bootstrap, Runtime, Command)

### `src/Runtime`

Слой, отвечающий за инициализацию окружения приложения.

- **`RuntimeBootstrap`**: Главный класс-инициализатор. Вызывается самым первым из `ytd.php`. Загружает переменные окружения через Symfony Dotenv, определяет корневую директорию проекта (`YTD_PROJECT_ROOT`), загружает `.env` и валидирует входные данные командной строки.
- **`ProcessEnvironment`**: Хранит провалидированные пути (к папкам загрузок, логам, `proxy_rules.yaml`) и переменные, необходимые для всего времени жизни процесса.
- **`RuntimeOptions`**: Data Transfer Object (DTO), в котором хранятся все параметры, переданные пользователем в командной строке (например, флаги `--fast`, `--quality`, выбранный прокси).

### `src/Command`

Интерфейс командной строки на базе Symfony Console.

- **`YtdCommand`**: Единственная команда приложения. Принимает аргументы (URL) и опции (`--audio`, `--fast`, `--mp4`), преобразует их в объект `RuntimeOptions`, определяет маршрут с помощью `RoutingService` и передает управление либо `SingleVideoFlowService`, либо `PlaylistFlowService`.
- **`YtdCommand`** не содержит никакой бизнес-логики скачивания, только оркестрацию флоу.

## 2. Маршрутизация (Routing)

### `src/Routing`

Модуль, определяющий, через какой прокси пускать трафик для конкретного домена.

- **`RoutingService`**: Читает файл `proxy_rules.yaml`. Анализирует переданный пользователем URL, извлекает хост и ищет совпадение (включая wildcard-паттерны `*.`) в трех секциях:
  1. `direct` (без прокси)
  2. `local` (прокси по умолчанию для локального региона, например `127.0.0.1:1080`)
  3. `remote` (внешний прокси, например, сервер за рубежом)
- **`RouteDecision` / `RoutingRule`**: DTO-объекты, возвращающие итоговый результат: использовать ли прокси, и если да, то какой именно.

## 3. Бизнес-логика скачивания (Download)

Это самое большое ядро приложения, в котором собрана логика взаимодействия с `yt-dlp`.

### `src/Download/SingleVideoFlowService`

Оркестратор скачивания одного видео. В зависимости от флагов решает, что делать:

- **`--fast`**: Передает управление в `FastStreamDownloadService` для параллельной загрузки видео и аудио потоков.
- **`--manual`**: Запускает интерактивный запрос `yt-dlp -F` и просит пользователя выбрать нужный формат (через `InputPrompter`).
- **Default**: Автоматически выбирает формат (`best`, `medium`, `low` или `bestaudio`) и отправляет задачу в `DownloaderService`.

### `src/Download/DownloaderService`

Низкоуровневый исполнитель, который выполняет preflight проверки (не существует ли уже такой файл, чтобы спросить о перезаписи) и вызывает `DownloadProcessRunner`. Отвечает за очистку временных файлов (`DownloadArtifactCleaner`), если процесс скачивания прервался с ошибкой.

### `src/Download/YtDlp`

Фасад для бинарника `yt-dlp`:

- **`YtDlpCommandBuilder`**: Строитель аргументов. Собирает массивы параметров (пути, прокси, форматы, таймауты, user-agent) в единую строку команды `Symfony\Component\Process\Process`.
- **`YtDlpProgressRenderer`**: Парсит `stdout` процесса `yt-dlp` в реальном времени, извлекая проценты загрузки, скорость и ETA (Estimated Time of Arrival) для красивого отображения прогресса в консоли (или передачи в Chrome расширение).

### `src/Download/FastStreamDownloadService`

Специальный режим (`--fast`), который через `yt-dlp` запрашивает прямые URL потоков (видео и аудио) и запускает их параллельное скачивание через встроенные PHP потоки (или `curl`), а затем склеивает через `ffmpeg`. Это в разы ускоряет загрузку с некоторых платформ.

## 4. Списки воспроизведения (Playlist)

Отдельный флоу для работы с плейлистами или каналами.

### `src/Playlist/PlaylistFlowService`

Оркестрирует флоу плейлиста:

1. Запрашивает метаданные плейлиста через `PlaylistMetadataService` (выполняет `yt-dlp --flat-playlist -J`).
2. Парсит JSON-ответ и создает набор объектов `PlaylistItem`.
3. Показывает сводку по размеру плейлиста и спрашивает подтверждение.
4. Выполняет preflight-проверки (оценка суммарного размера файлов на диске).
5. Запускает `PlaylistDownloadQueueRunner`.

### `src/Playlist/PlaylistDownloadQueueRunner`

Специальный компонент, который берет массив из элементов плейлиста и скачивает их. В зависимости от настройки `--concurrent-downloads`, он может скачивать несколько видео параллельно через асинхронные процессы Symfony.

## 5. Интеграция с браузером (NativeHost)

Уникальная часть проекта, позволяющая Chrome-расширению общаться с PHP-скриптом напрямую через механизм **Native Messaging Protocol**.
Расширение шлет JSON сообщения в `stdin` процесса PHP, а PHP отвечает в `stdout`, предварительно кодируя длину сообщения в первые 4 байта.

### `src/NativeHost/Protocol`

Реализует низкоуровневый протокол общения браузера и хоста.

- **`NativeMessagingProtocolService`**: Читает ровно 4 байта длины сообщения из `stdin`, затем `N` байт JSON payload'а. Для отправки ответа сначала пишет 4 байта длины ответа.
- **`NativeHostHandlerService`**: Маршрутизатор запросов от Chrome. Принимает JSON, мапит его в объекты Request (`StartDownloadRequest`, `ListRecentDownloadsRequest`) и вызывает соответствующий сервис.

### `src/NativeHost/Job`

Управляет фоновыми задачами скачивания.

- Поскольку Native Messaging требует, чтобы процесс жил, пока нужно общаться с браузером, долгие скачивания (видео) запускаются в фоне (через `NativeHostJobRunnerService`).
- **`NativeHostProgressParserService`**: Читает лог-файл фонового процесса `yt-dlp` и парсит его, чтобы вернуть в Chrome текущий прогресс (проценты, скорость).

### `src/NativeHost/Preview`

В расширении есть отдельная вкладка "Preview" (предпросмотр перед скачиванием).

- `NativeHostPreviewServerService` запускает временный HTTP-сервер на PHP (`php -S localhost:PORT`), чтобы браузер мог запрашивать данные, не дожидаясь ответа через блокирующий Native Messaging.

## 6. Диагностика (Diagnostics)

### `src/Diagnostics/DoctorService`

Вызывается флагом `--doctor`. Проверяет:

- Установлены ли бинарники `yt-dlp` и `ffmpeg` и доступны ли они в `$PATH`.
- Скопированы ли и заполнены ли конфигурационные файлы `.env` и `proxy_rules.yaml`.
- Созданы ли директории для загрузок (разрешена ли запись).
- Работает ли сеть через выбранные прокси.

Выводит красивую зелено-красную таблицу с результатами проверок, чтобы пользователь мог сразу понять, почему скрипт не работает.

## Правила архитектуры (Deptrac)

Проект строго следит за отсутствием циклических или нелогичных зависимостей:

1. **Command** зависит от **Service** и **Runtime**.
2. Никакой класс из **Download** или **Playlist** не может знать про интерфейс командной строки (флаги, стили консоли). Они общаются через абстрактные DTO.
3. **DTO** не содержат никакой логики и не зависят ни от одного другого слоя.
4. **NativeHost** может вызывать бизнес-логику из **Download**, но бизнес-логика ничего не знает о NativeHost.
